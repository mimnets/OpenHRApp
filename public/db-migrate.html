Move the database to the self-hosted server

From Supabase Pro to api.openhrapp.com. The steps are in order. Real users are not affected until step 4.

1Connect to the server

This page sends commands to a small helper on the OCI server. In PuTTY, start the helper:

cd ~/OpenHRApp && git pull
python3 scripts/migrate-to-selfhost/migrate-runner.py

Do the two setup steps that it prints (one command, and one setting in Nginx Proxy Manager). Then paste the token it prints.

Helper address

2Enter the Pro details and run the checks

These are sent to your server only, with each command, and are not saved. Reloading this page clears them.

    3Test copy

    Copies everything to the self-hosted server while the app stays on Pro. You can repeat this. Cron jobs stay paused on the self-hosted server, so nobody gets a reminder twice.

    The self-hosted database already has data. A new copy replaces it. A backup is saved on the server first.
    Test it before the switch (recommended)
    1. In Vercel, set VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY for Preview only, with the values shown in step 4.
    2. Open a preview deployment. Log in as an admin and as an employee, open attendance and leave, and view a selfie.
    3. Do not enter real data. This copy is replaced in the next step.

    4Final switch

    Do this at a quiet time. It pauses cron on Pro, copies the newest data and files, and turns cron on here.

    Anything users enter on Pro after this copy starts does not move across. Finish the Vercel switch right after the copy.
    The copy finished with differences or failed files (see the log). Small row differences are normal if users were active during the copy. If only the files failed because Pro is restricted, you can accept, switch, and use "Copy the files" in step 3 after the restriction is lifted. It then copies only missing files. Otherwise, run the final copy again.

    Vercel values

    Project → Settings → Environment Variables. Use these for Production only after the final copy, then redeploy the latest production deployment.

    After the redeploy, test on openhrapp.com

    1. Log in, check in and check out, and apply for leave.
    2. Register a test organization, and check that the code email arrives.
    3. In Resend → Emails, check that the emails are delivered.

    5Revert to Supabase Cloud, or finish

    Revert: copy everything back to Supabase Cloud

    Use this when the app runs on the self-hosted server and you want to go back, with all data entered since the switch. It works only after the final switch, and only into the original Cloud project. If that project is paused, restore it in the Supabase dashboard first.

    1. Pick a quiet time. Anything users enter during the copy does not move across.
    2. Run the copy below. It backs up Cloud on your server, replaces Cloud's data in one transaction, copies the files, and compares row counts.
    3. When it succeeds, set VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY in Vercel back to the Cloud values, and redeploy.
    This replaces all data in the Cloud project with the data on this server.
    The copy finished with differences or failed files (see the log). The self-hosted server is still live. Run the copy again at a quiet time, or accept them if they are expected.
    Quick rollback, without copying data

    Only for right after the switch, if no one has entered data worth keeping. First set the two Vercel values back to Cloud, and redeploy. This turns cron back on at Cloud and pauses it here. Data entered on this server stays here.

    When you finish, stop the helper. Then remove the /db-migrate-runner/ block from Nginx Proxy Manager.
